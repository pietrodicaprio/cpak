# cpak experimental POC CA certificate policy and practice statement

Status: experimental, development-only  
Policy identifier: `1.3.6.1.4.1.55555.1.1`  
Assurance label: `experimental-private-pki`

This concise CP/CPS documents a self-contained demonstration hierarchy. The
policy identifier is an intentionally experimental placeholder under a private
enterprise arc not claimed by this project. A production CA must use an OID it
controls and publish an independently reviewed CP/CPS.

## Purpose and relying-party boundary

The hierarchy demonstrates detached CMS code signing and offline certificate
validation for Linux application artifacts. It performs no legal-identity or
organisation validation. Relying parties explicitly import a generated root
into cpak's dedicated Code Signing root store. The operating-system TLS root
store and cpak's embedded public root program are outside this hierarchy.

Acceptance of a signature proves only that the corresponding publisher key
signed the exact canonical state. It does not establish software safety,
publisher reputation, public trust, or origin ownership beyond the signed
state.

## Hierarchy and profiles

The offline root is self-signed, has `CA=true`, `keyCertSign` and `cRLSign`, and
permits one subordinate-CA level. It signs only the two dedicated
intermediates; it never signs publisher or TSA leaves directly.

The Code Signing intermediate has `CA=true`, `pathLen=0`, `keyCertSign` and
`cRLSign`. It issues leaves with `CA=false`, `digitalSignature`, exactly the
Code Signing EKU, a 90-day lifetime, and a bounded subject containing only the
publisher display name used by this demonstration.

The timestamping intermediate is a distinct `pathLen=0` CA. Its leaves have
`CA=false`, `digitalSignature`, and exactly the Time Stamping EKU. Trust in a
Code Signing root purpose never grants timestamping authority; the cpak trust
store admits those purposes separately.

All keys generated by the supplied tool are ECDSA P-256. Certificate and CRL
signatures use SHA-256. CMS signatures use SHA-256 and carry the publisher leaf
and intermediate but not a trust root.

## Generation and private-key handling

`hack/poc-ca` is development tooling and is not linked into the production cpak
runtime. It creates a new output directory with mode `0700`. Every private key
is emitted as encrypted PKCS#8 PEM with mode `0600`, scrypt (`N=32768`, `r=8`,
`p=1`, 16-byte salt), and AES-256-GCM; the passphrase is read from a separate
owner-only file and never accepted as a command-line argument.

Generated private material is disposable. It must remain outside the source
checkout, must never enter a container image or CI artifact, and must be removed
after the demonstration. The checked-in sample contains no reusable private
key or passphrase.

`cpak-sign x509-sign` consumes the publisher key through Go's `crypto.Signer`
boundary. A later PKCS#11 or hardware-token backend therefore does not alter
the CMS or signed-state formats.

## Issuance, revocation, and expiry

The POC tool performs local issuance only; it exposes no enrolment protocol or
network service. The generated CRL is an empty test CRL valid for seven days.
No OCSP responder exists. Revocation is evaluated only from administrator-
supplied offline CRLs according to cpak policy.

The POC does not implement certificate renewal, compromise response, audit-log
retention, subscriber identity proofing, or production key ceremonies. A
compromised generated key requires discarding the entire disposable hierarchy.

## Root distribution and opt-in

The POC root is never embedded or silently installed. An administrator previews
the root, confirms its lowercase SHA-256 certificate fingerprint, and imports
it specifically for `code-signing`. Removal affects subsequent full
verification only; it must not rewrite or corrupt existing enrolment records.

Public distribution of a root certificate is not equivalent to inclusion in a
trusted root program. Every relying machine must receive and explicitly admit
the root, or receive a separately managed cpak root bundle from its operator.
